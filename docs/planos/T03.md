# T03 — Fome

**Objetivo:** a fome do jogador cai com o tempo, mais rápido quando ele se move ou nada. Em 0, ele perde vida. Uma barra simples na tela mostra a fome.

**Pronto quando:** a barra desce sozinha e, com a fome em 0, a vida cai até o jogador morrer.

## Como a fome chega ao cliente

O servidor guarda a fome em `PlayerData.hunger` (já existe desde a T02) e espelha o valor num **atributo `Hunger` no `Player`**. Atributos que o servidor define replicam sozinhos para o cliente.

- **Por que atributo e não RemoteEvent:** é um valor de estado que muda o tempo todo e que só o servidor escreve. O atributo já faz a replicação, e o cliente só escuta `GetAttributeChangedSignal`. Um Remote exigiria código dos dois lados para fazer a mesma coisa. Isso não quebra a regra "serviço não chama controller": o serviço não chama nada, só publica um estado.
- **O servidor nunca lê o atributo.** A fonte da verdade é `PlayerData.hunger`. O cliente pode mudar o atributo na cópia local dele, mas isso não replica e só afeta o próprio HUD.
- É o mesmo padrão do `leaderstats.Dinheiro` na T02: o **DataService** é o único que escreve o espelho.

## `Config/Survival.luau`

```luau
return table.freeze({
	TICK_SECONDS = 1,                -- intervalo do loop da fome
	HUNGER_DRAIN_PER_SECOND = 0.1,   -- parado: 100 → 0 em ~16 min
	MOVING_MULTIPLIER = 1.5,         -- andando: ~11 min
	SWIMMING_MULTIPLIER = 2,         -- nadando: ~8 min
	MOVING_SPEED_THRESHOLD = 1,      -- studs/s na horizontal para contar como "andando"
	STARVE_DAMAGE_PER_SECOND = 5,    -- com vida 100: morre em ~20 s de fome zerada
	RESPAWN_MIN_HUNGER = 30,         -- fome mínima ao (re)nascer
})
```

- Os valores são provisórios; o balanceamento é da T12. A ideia é que 10 minutos de jogo peçam algumas idas aos mariscos (T04), sem virar castigo.
- `MAX_HUNGER` continua em `Config/Player.luau`, porque é também o valor inicial do save.

## `DataService.luau` — o que muda

1. **Nova função `SetHunger(player: Player, value: number): boolean`:**
   - Recusa (`false`) se não houver perfil ou se `value` for NaN (`value ~= value`).
   - Faz `math.clamp(value, 0, MAX_HUNGER)`. Assim, `math.huge` vira 100 e `-math.huge` vira 0.
   - Grava em `data.hunger` e faz `player:SetAttribute("Hunger", data.hunger)`.
   - A T04 (comer) também vai usar essa função.
2. **Ao carregar o perfil**, junto com o `createLeaderstats`, faça `player:SetAttribute("Hunger", data.hunger)`, para o HUD já começar certo.

Não crie `AddHunger`: quem chama faz `SetHunger(player, data.hunger + x)`.

## `Services/HungerService.luau`

### `Init()`
Nada obrigatório. Pode ficar sem `Init`, porque o Loader aceita.

### `Start()`

**1. Loop da fome.** Rode com `task.spawn`:

```
while true do
	local dt = task.wait(TICK_SECONDS)
	for each player in Players:GetPlayers():
		tick(player, dt)
end
```

Use o `dt` que o `task.wait` devolve, não o `TICK_SECONDS`. Se o servidor atrasar, a fome continua certa.

**2. `tick(player, dt)`:**
- Pegue `data = DataService.GetData(player)`. Se for `nil`, pule: o save ainda não carregou.
- Pegue o `Humanoid` do `player.Character` e o `HumanoidRootPart`. Se faltar algum, ou se `humanoid.Health <= 0`, pule. **Morto não passa fome.**
- Calcule o multiplicador:
  - Nadando (`humanoid:GetState() == Enum.HumanoidStateType.Swimming`): `SWIMMING_MULTIPLIER`.
  - Senão, se a velocidade horizontal do `HumanoidRootPart` (`AssemblyLinearVelocity` com Y zerado, `.Magnitude`) for maior que `MOVING_SPEED_THRESHOLD`: `MOVING_MULTIPLIER`.
  - Senão: `1`.
- `DataService.SetHunger(player, data.hunger - HUNGER_DRAIN_PER_SECOND * multiplier * dt)`.
- Se, depois disso, `data.hunger <= 0`, faça `humanoid:TakeDamage(STARVE_DAMAGE_PER_SECOND * dt)`.
  - Use `TakeDamage` e não `Health -=`. O `TakeDamage` respeita o `ForceField` do spawn.
  - O script padrão de regeneração do Roblox recupera cerca de 1% da vida por segundo. Com 5/s de dano, a vida ainda cai. Não mexa nele.

**3. Fome mínima ao renascer.**
- Em `Players.PlayerAdded` e para os jogadores que já estão no servidor, conecte `player.CharacterAdded`.
- Nesse evento, se `data` existir e `data.hunger < RESPAWN_MIN_HUNGER`, chame `SetHunger(player, RESPAWN_MIN_HUNGER)`.
- Sem isso, quem morre de fome renasce com 0 e morre de novo em 20 segundos, sem fim.
- **Limitação conhecida:** resetar o personagem pelo menu devolve a fome para 30. Aceitável no M1, porque a morte vai custar os peixes não vendidos (GDD 2.9, em tarefa futura). Anote no código com um comentário `-- ponytail:`.
- Se o save carregar depois do `CharacterAdded` (o save é mais lento que o personagem), essa checagem pula esse spawn. Tudo bem: o save já traz a fome salva, e quem saiu com 0 ainda tem 20 segundos para comer.

### Risco: nado detectado no servidor
O estado do Humanoid é controlado pelo cliente, e **não sei** se `GetState()` no servidor devolve `Swimming` de forma confiável. Hoje não existe água no mapa (ela vem na T11), então esse caso não dá para testar agora.

## Segurança

- Não há entrada do cliente nesta tarefa: o cliente só lê o atributo.
- O servidor usa `PlayerData.hunger` como fonte da verdade e nunca lê o atributo `Hunger`.
- `SetHunger` recusa NaN e limita o valor a `0..MAX_HUNGER`. Nenhum chamador futuro consegue gravar fome inválida no save.
- O dano de fome usa `TakeDamage` no servidor.
- **Aceitável:** o cliente controla a física do próprio personagem e pode ficar "parado" para gastar menos fome. O ganho é pequeno, e qualquer checagem de movimento no servidor teria esse mesmo limite.

## Como testar

Siga a memória da T02: o `execute_luau` **não enxerga** o estado dos serviços. Para chamar o DataService, use um script temporário e apague no fim. Instâncias e atributos reais dão para ler pelo `execute_luau` no datamodel **Server**.

### 1. A barra e a drenagem
- Rode o play mode. O Output deve mostrar `Servidor iniciado` e `Cliente iniciado`, sem erro. A barra deve aparecer no canto inferior esquerdo.
- Leia `player:GetAttribute("Hunger")` duas vezes, com uns 5 segundos de intervalo, pelo `execute_luau` (Server). Parado, deve cair cerca de `0.1 × 5 = 0.5`.
- Tire uma foto da tela com `screen_capture` e confira a barra.

### 2. Andar gasta mais
- Mova o personagem com `character_navigation` e leia o atributo antes e depois. A queda por segundo deve ficar perto de 1.5× a de parado.

### 3. Fome zero tira vida
- Crie `ServerScriptService/_TesteFome.server.luau`: espere o `GetData` deixar de ser `nil` e chame `DataService.SetHunger(player, 0)`.
- Pelo `execute_luau`, leia `Humanoid.Health` algumas vezes: ela deve cair cerca de 5 por segundo, menos a regeneração, até o jogador morrer.
- Depois de renascer, o atributo `Hunger` deve estar em `30`.

### 4. Validações do `SetHunger`
No mesmo script temporário:
- `SetHunger` com `0/0` → `false`, e a fome não muda.
- `SetHunger(200)` → `data.hunger == 100`.
- `SetHunger(-5)` → `data.hunger == 0`.

### 5. Persistência
Com uma fome diferente de 100, pare o play mode e rode de novo: a barra deve voltar com o mesmo valor.

### Limpeza
- Apague o `_TesteFome.server.luau`.
- **Salve o place no Studio**, para não perder o `HungerGui`.
