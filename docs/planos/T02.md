# T02 — DataService (save)

**Objetivo:** salvar e carregar os dados de cada jogador com o ProfileStore. O serviço expõe `GetData`, `AddMoney`, `AddItem` e `RemoveItem`, e mostra o dinheiro no `leaderstats`.

**Pronto quando:** o jogador ganha dinheiro por um script de teste, sai, volta, e o valor continua lá.

---

## Pré-requisito (manual, no Studio)

Ative **Game Settings → Security → Enable Studio Access to API Services**. O place precisa estar publicado.

Sem isso, o ProfileStore entra em **modo mock**: ele funciona, mas não salva nada entre sessões e só mostra um aviso no Output. Se o teste de persistência falhar, confira isso primeiro.

## ProfileStore (módulo de terceiros)

- **Fonte:** https://github.com/MadStudioRoblox/ProfileStore, arquivo `ProfileStore.luau` da branch `main`. É a versão **1.0.3** (wally.toml), commit `45c9847`, de 31/07/2025. Baixe com:
  `gh api repos/MadStudioRoblox/ProfileStore/contents/ProfileStore.luau -H "Accept: application/vnd.github.raw" > ServerScriptService/Packages/ProfileStore.luau`
- **Não edite o arquivo.** Ele não tem `--!strict` no topo, e isso é esperado. Anote a versão e o commit na mensagem do commit.
- **Já conferi:** o módulo não tem `loadstring` nem `require` de id numérico. O único `require` é uma linha comentada.
- Ele trata o `BindToClose` sozinho, salvando os perfis quando o servidor fecha. O DataService **não** precisa de `BindToClose` próprio.
- `Packages/` fica fora de `Services/`, então o Loader não tenta carregar o ProfileStore como serviço.
- **AGENTS.md:** acrescente em "Como o projeto sincroniza" a linha: "`ServerScriptService/Packages/` guarda código de terceiros: não editar; as regras de estilo (ex.: `--!strict`) não se aplicam."

API usada (conferida no código-fonte e no tutorial oficial):
- `ProfileStore.New(storeName, template)`
- `store:StartSessionAsync(key, { Cancel = fn })`, que devolve `Profile` ou `nil`
- `profile:AddUserId(userId)`, `profile:Reconcile()`, `profile:EndSession()`
- `profile.Data`, `profile.OnSessionEnd`
- O tipo exportado é `ProfileStore.Profile<T>`

## Dados

### `Types.luau` — tipos novos

```luau
export type ItemData = {
	id: string,        -- id de um config (Fish, Lures...)
	weight: number?,   -- kg; só peixes
}

export type PlayerData = {
	money: number,
	inventory: { [string]: ItemData },  -- chave = uid do item
	equippedRod: string?,               -- id em Rods; nil = sem vara
	equippedLure: string,               -- id em Lures
	hunger: number,                     -- 0..100
}
```

Por que cada escolha:
- **O inventário é um dicionário por uid** (`HttpService:GenerateGUID(false)`), não uma lista. Cada peixe é único (o peso muda o preço), e a venda da T09 vai precisar dizer "vender *este* peixe". O uid dá uma referência estável para o Remote. Uma lista teria buracos ao remover, e o ProfileStore não aceita tabela numérica com buracos.
- **Itens iguais não se empilham.** Duas salsichas são dois itens. Isso é simples e basta para o M1, porque o limite de itens segura o tamanho do save.
- **Varas e armas compradas ficam de fora.** Quando a T05/T10 precisar saber se o jogador tem a faca, ela acrescenta o campo. O `Reconcile` preenche campos novos em saves antigos.
- **`equippedRod` pode ser `nil`**, porque o jogador começa sem vara (a Vara de Siri custa $3, GDD). Não coloque esse campo no template: o `Reconcile` só preenche o que falta, e campo `nil` não existe na tabela.

### `Config/Player.luau`

```luau
return table.freeze({
	STARTING_MONEY = 0,
	STARTING_LURE = "isca_gratis",
	MAX_HUNGER = 100,
	MAX_INVENTORY_ITEMS = 100,
})
```

- `MAX_HUNGER` também é o valor inicial da fome. A T03 cria o `Survival.luau` para o resto (velocidade de drenagem etc.). Aqui fica só o que o save precisa.
- `MAX_INVENTORY_ITEMS` segura o tamanho do save. Um DataStore aceita até 4 MB por chave, e um inventário sem limite é vetor de abuso.
- Não precisa de tipo em `Types.luau`: `table.freeze` de uma tabela literal já dá o tipo inferido.

## `Services/DataService.luau`

Constantes no topo do arquivo (não são balanceamento):
- `STORE_NAME = "PlayerData_v1"`. Troque o sufixo se um dia o formato mudar de forma incompatível.
- A chave do jogador é `"Player_" .. player.UserId`.

### `Init()`
- Monte o template a partir do `Config/Player`: `money`, `inventory = {}`, `equippedLure`, `hunger`. **Sem** `equippedRod`.
- `store = ProfileStore.New(STORE_NAME, template)`.
- Guarde os perfis carregados numa tabela privada: `profiles: { [Player]: Profile }`.

### `Start()`
Siga o padrão do tutorial oficial:
1. `Players.PlayerAdded:Connect(onPlayerAdded)`. Rode `onPlayerAdded` com `task.spawn` também para os jogadores que já estão em `Players:GetPlayers()`.
2. **`onPlayerAdded(player)`:**
   - Chame `StartSessionAsync(key, { Cancel = function() return player.Parent ~= Players end })`.
   - Se vier `nil`, faça `player:Kick("Não foi possível carregar seus dados. Entre de novo.")` e pare.
   - Faça `profile:AddUserId(player.UserId)` (GDPR) e `profile:Reconcile()`.
   - Conecte `profile.OnSessionEnd`: tire o jogador de `profiles` e chame `player:Kick("Sessão encerrada. Entre de novo.")`. Isso cobre outro servidor pegando a sessão. Quando o jogador sai normalmente, o kick acontece com ele já saindo e não tem efeito.
   - Se o jogador já saiu enquanto carregava (`player.Parent ~= Players`), chame `profile:EndSession()` e pare.
   - Guarde o perfil em `profiles[player]` e crie o `leaderstats`.
3. **`Players.PlayerRemoving`:** se existir `profiles[player]`, chame `:EndSession()`. Não precisa remover da tabela aqui, porque o `OnSessionEnd` já remove.

### leaderstats (provisório)
- Crie um `Folder` com o nome `leaderstats` (exatamente assim, o Roblox procura esse nome) dentro do `player`, e dentro dele um `IntValue` chamado `Dinheiro`, com `Value = data.money`.
- Quem cria é o **servidor**. O cliente não consegue alterar o valor que o servidor vê.
- `AddMoney` atualiza o `IntValue`. Não use o `IntValue` como fonte da verdade: ele só espelha `data.money`.

### API pública

Todas as funções são só para o servidor e **nunca** podem ser chamadas diretamente com argumentos vindos de Remote. Quem expõe algo ao cliente (T04, T09, T10) valida primeiro e depois chama o DataService.

| Função | Retorno | Regras |
|---|---|---|
| `GetData(player: Player)` | `PlayerData?` | `nil` se o perfil ainda não carregou (ou já saiu). Quem chama **tem que** tratar o `nil`. Devolve a tabela viva: só leitura por convenção. Mudanças passam pelas funções abaixo, para o leaderstats e as validações ficarem num lugar só. |
| `AddMoney(player, amount: number)` | `boolean` | Recusa (`false`) se não houver perfil, se `amount` não for inteiro, se for `<= 0`, ou se for NaN/infinito. Use `amount == math.floor(amount)` e `amount < math.huge`; NaN falha em qualquer comparação. |
| `AddItem(player, item: ItemData)` | `string?` (uid) | Recusa (`nil`) se não houver perfil, se o inventário estiver cheio (`MAX_INVENTORY_ITEMS`) ou se `item.id` não existir em `Fish` nem em `Lures`. Guarda **uma cópia** (`{ id = item.id, weight = item.weight }`), nunca a tabela recebida. |
| `RemoveItem(player, uid: string)` | `ItemData?` | Devolve o item removido, ou `nil` se o uid não existir. |

**Ficou de fora de propósito (YAGNI):**
- `SpendMoney`/checar saldo: entra na T10 (loja).
- Setter de fome: T03.
- Setter de vara/isca equipada: T05/T10.
- Sinal de "perfil carregado": quem precisar do dado trata o `nil` do `GetData`.
- O `marisco` (T04) vai ter que entrar no conjunto de ids que o `AddItem` aceita. Monte esse conjunto uma vez no `Init`, a partir dos configs, para a T04 só acrescentar o config dela.

## Objetos no Studio (MCP)

Nenhum. O `leaderstats` é criado por código, em tempo de jogo.

## Segurança

- Nenhum Remote nesta tarefa. O cliente não consegue chamar o DataService.
- O session lock do ProfileStore impede que o mesmo save fique aberto em dois servidores, o que evita duplicar itens.
- `AddMoney` recusa valor negativo, fracionário, NaN e infinito. Um bug ou Remote mal validado no futuro não consegue zerar nem estourar o dinheiro por aqui.
- `AddItem` só aceita id que existe nos configs e copia o item, então quem chamou não consegue alterar o save depois por uma referência à tabela.
- O limite de itens protege o tamanho do save.
- Se o save não carregar, o jogador é expulso. Jogar sem save arriscaria sobrescrever o progresso dele com dados vazios.

## Como testar

### 1. Carregamento
Rode o play mode. O Output deve mostrar `Servidor iniciado` e `Cliente iniciado`, sem erro. O placar (Tab) deve mostrar a coluna **Dinheiro**.

Se aparecer aviso do ProfileStore sobre falta de acesso à API ou modo mock, volte ao pré-requisito.

### 2. Persistência
Primeiro, tente dar o dinheiro pelo MCP, com `execute_luau` no datamodel **Server** durante o play:

```luau
local DataService = require(game:GetService("ServerScriptService").Services.DataService)
local player = game:GetService("Players"):GetPlayers()[1]
return DataService.AddMoney(player, 10), DataService.GetData(player)
```

- **Se `GetData` vier `nil`**, o `execute_luau` está com um cache de `require` diferente do jogo, e a instância dele não tem o perfil carregado. Nesse caso, crie o script temporário `ServerScriptService/_TesteDinheiro.server.luau`: ele espera o `GetData` deixar de ser `nil` e chama `AddMoney(player, 10)` uma vez. Apague esse arquivo depois do teste.
- Depois de dar o dinheiro, pare o play mode. O ProfileStore salva no `BindToClose`.
- Rode o play mode de novo (sem o script temporário). O **Dinheiro** precisa mostrar o mesmo valor.

### 3. Validações do `AddMoney` e do `AddItem`
Pelo mesmo caminho do teste 2 (MCP ou script temporário):
- `AddMoney` com `-5`, `1.5`, `0/0` e `math.huge` → `false` e o dinheiro não muda.
- `AddItem({ id = "nao_existe" })` → `nil`.
- `AddItem({ id = "siri", weight = 0.8 })` → devolve um uid. Depois, `RemoveItem` com esse uid devolve o item, e um segundo `RemoveItem` devolve `nil`.

### 4. Limpeza
Depois dos testes, zere o dinheiro de teste (`data.money = 0` pelo mesmo caminho) ou deixe como está, mas anote no resumo. Não use `RemoveAsync` em produção.

Arquivos tocados, qual caminho de teste funcionou (MCP ou script temporário), o Output dos testes 1 e 2 e se o ProfileStore rodou com acesso real ou em mock.
