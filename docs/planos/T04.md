# T04 — Mariscos

**Objetivo:** o jogador pega mariscos no chão com `E`, eles vão para o inventário e reaparecem depois de um tempo. Com o marisco na mão, segurar o clique come e recupera a fome.

**Pronto quando:** pegar um marisco, comer, a fome sobe, e o marisco reaparece no chão.

## Decisões

### Como o jogador vê e segura o marisco: uma Tool
Ainda não existe tela de inventário (o menu de venda é da T09). A forma mais simples de ter "item na mão + segurar clique" no Roblox é uma **Tool** na mochila:
- O servidor mantém **uma** Tool "Marisco" na mochila enquanto o inventário tiver pelo menos um marisco.
- O nome da Tool mostra a quantidade: `Marisco (3)`. É isso que aparece na barra de itens.
- A Tool é criada por código (`Instance.new("Tool")`) e não pelo MCP, porque ela aparece e some conforme o inventário. A regra do AGENTS.md sobre criar ferramentas pelo MCP vale para as ferramentas fixas do StarterPack, como a vara da T05.
- Configuração: `RequiresHandle = false` (não precisa de modelo), `CanBeDropped = false` (senão `Backspace` joga a Tool no chão, e ela sairia de sincronia com o save) e o atributo `FoodId = "marisco"`, usado pelo cliente e pelo servidor para reconhecer a Tool.
- **A fonte da verdade continua sendo o inventário do save.** A Tool só espelha, como o `leaderstats` e o atributo `Hunger`.

### Um serviço só
O `FoodService` cuida de pegar mariscos, comer e manter a Tool. Tudo gira em volta de comida, e fica bem abaixo de 200 linhas. Quando o peixe cru e o assado puderem ser comidos (GDD 2.1 e 2.7), eles entram no mesmo serviço, só com mais entradas no `Food.luau`.

### Esperar o save carregar: `DataService.WaitForData`
Agora são três lugares que precisam do save no `CharacterAdded`: a Tool do marisco, que some da mochila ao morrer, a fome mínima da T03 e, logo, a vara. O save costuma carregar **depois** do personagem aparecer. Por isso:

```luau
-- Espera o save carregar. nil se o jogador sair antes.
function DataService.WaitForData(player: Player): Types.PlayerData?
```

A implementação espera em loop com `task.wait(0.5)` enquanto `GetData` for `nil` e `player.Parent == Players`. Isso é simples e basta: o save carrega em poucos segundos. Troque para um sinal só se aparecer um problema real.

- **Na T03 (HungerService):** o `onCharacterAdded` passa a usar `WaitForData` dentro de um `task.spawn`. Isso corrige o caso anotado na T03, em que o save carregava depois do personagem e a checagem de fome mínima era pulada.

### `Config/Survival.luau` — acrescentar
```luau
MARISCO_RESPAWN_SECONDS = 30,    -- tempo até o marisco reaparecer
PICKUP_MAX_DISTANCE = 10,        -- studs; o servidor recusa se o jogador estiver mais longe

```

## `Services/FoodService.luau`

Estado privado:
- `available: { [BasePart]: boolean }`: se cada marisco está no chão.
- `lastEatAt: { [Player]: number }`: o `os.clock()` da última refeição. Limpe no `PlayerRemoving`.

### `refreshFoodTool(player)`
1. Conte os itens `marisco` no inventário (`GetData`).
2. Procure a Tool com o atributo `FoodId == "marisco"` no `Backpack` **e** no `Character` (ela fica no personagem quando está equipada).
3. Se a contagem for 0, destrua a Tool, se existir.
4. Se for maior que 0, crie a Tool se não existir (no `Backpack`) e ajuste o nome para `Marisco (n)`.

Chame essa função depois de pegar, depois de comer e no `CharacterAdded`, dentro de `task.spawn`, depois do `WaitForData`, porque a mochila é esvaziada a cada morte.

### Pegar marisco: `ProximityPrompt.Triggered(player)`
Conecte o evento de cada Part no `Start`. Valide **nesta ordem**:
1. `available[part]` é `true`.
2. O personagem existe, tem `Humanoid` com vida acima de 0 e tem `HumanoidRootPart`.
3. A distância entre o `HumanoidRootPart` e a Part é no máximo `PICKUP_MAX_DISTANCE`. Use as posições do servidor e não confie no prompt, porque um exploit consegue disparar o prompt de longe.
4. `DataService.AddItem(player, { id = "marisco" })` devolve um uid. Se vier `nil` (inventário cheio), **não** consuma o marisco e pare.

Se tudo passar:
- Marque `available[part] = false`, deixe a Part invisível (`Transparency = 1`) e faça `prompt.Enabled = false`.
- Chame `refreshFoodTool(player)`.
- Com `task.delay(MARISCO_RESPAWN_SECONDS, ...)`, devolva a transparência original e reative o prompt e o `available`.

Não há corrida entre dois jogadores: o servidor roda um evento por vez, e o `available` é checado e marcado sem nenhum `yield` entre um e outro.

### Comer: `Remotes.EatFood.OnServerEvent(player, foodId)`
Valide **nesta ordem** e ignore sem erro se falhar:
1. `typeof(foodId) == "string"` e `Food[foodId] ~= nil`.
2. Intervalo: `os.clock() - (lastEatAt[player] or 0) >= EAT_MIN_INTERVAL_SECONDS`. Isso limita spam e garante no servidor o "segurar por um tempo".
3. Personagem vivo e **com a Tool dessa comida equipada**, ou seja, um filho do `Character` com o atributo `FoodId == foodId`.
4. `data = GetData(player)` existe e `data.hunger < MAX_HUNGER`. Comer com a fome cheia só desperdiçaria o item.
5. Existe no inventário um item com `id == foodId`. Pegue o uid dele.

Se tudo passar:
- Atualize `lastEatAt[player]`.
- Chame `DataService.RemoveItem(player, uid)` e depois `DataService.SetHunger(player, data.hunger + food.hungerRestore)`.
- Chame `refreshFoodTool(player)`.

O cliente manda **só o id da comida**. Quanto a fome sobe é decidido pelo `Food.luau` do servidor.

## `Controllers/FoodController.luau`

- No `CharacterAdded` (e no personagem atual, se já existir), escute `character.ChildAdded`. Quando entrar uma `Tool` com o atributo `FoodId`, a Tool foi equipada. Conecte:
  - `tool.Activated`: comece a segurar. Guarde um contador (`holdId += 1`) e faça `task.delay(EAT_HOLD_SECONDS, ...)`. Se, quando o delay terminar, o `holdId` for o mesmo e a Tool continuar no personagem, faça `Remotes.EatFood:FireServer(tool:GetAttribute("FoodId"))`.
  - `tool.Deactivated` e `tool.Unequipped`: `holdId += 1`, o que cancela a espera.
- Segurar de novo depois de comer exige soltar e clicar outra vez. Não há repetição automática.
- Pegue o Remote com `ReplicatedStorage:WaitForChild("Remotes"):WaitForChild("EatFood")`.
- Sem barra de progresso nem animação por enquanto: a resposta visual é a barra de fome subindo e o número na Tool diminuindo. Se ficar confuso no playtest, a T12 decide.

## Segurança (resumo)

| Entrada do cliente | Validação no servidor |
|---|---|
| Prompt do marisco | marisco disponível, jogador vivo, distância real ≤ `PICKUP_MAX_DISTANCE`, espaço no inventário |
| `EatFood(foodId)` | tipo string, id existe no `Food`, intervalo mínimo, jogador vivo com a Tool daquela comida equipada, fome abaixo do máximo, item no inventário |

- O cliente nunca informa quanto de fome recupera nem quantos itens tem.
- A Tool é só um espelho. Se um exploit criar uma Tool falsa com `FoodId` no próprio personagem, ela não replica para o servidor, e mesmo assim o servidor ainda exigiria o item no inventário.
- `lastEatAt` é limpo quando o jogador sai.

## Como testar

Siga o padrão das tarefas anteriores: o `execute_luau` não enxerga o estado dos serviços. Instâncias, atributos e o disparo de Remotes pelo cliente funcionam normalmente.

### 1. Estrutura
No Edit, confira `Workspace.Mariscos` com 6 Parts e um `ProximityPrompt` em cada, e `ReplicatedStorage.Remotes.EatFood`. Espere uns segundos e confira de novo que o `EatFood` continua lá, sem ter sido apagado pelo Script Sync.

### 2. Pegar
- No play, leve o personagem até um marisco com `character_navigation` e aperte `E` com `user_keyboard_input`.
- No servidor, confira que a Part ficou com `Transparency = 1` e que existe no `Backpack` uma Tool `Marisco (1)`.
- Se a tecla pelo MCP não disparar o prompt, use um script temporário que chama a mesma função de coleta, e anote isso no resumo.
- Depois de cerca de 30 segundos, a Part volta a ficar visível.

### 3. Comer
- Deixe a fome abaixo de 100 com um script temporário que chama `SetHunger(player, 50)`. Pode ser o mesmo script da coleta.
- Equipe a Tool pelo `execute_luau` no **Client** (`humanoid:EquipTool(tool)`). Depois, dispare `Remotes.EatFood:FireServer("marisco")`, ou segure o clique com `user_mouse_input`, se ele permitir.
- O atributo `Hunger` deve subir 15, e a Tool deve sumir, porque a contagem voltou a 0.

### 4. Recusas (disparando o Remote pelo Client)
Em cada caso, a fome e o inventário não podem mudar:
- `FireServer(123)` e `FireServer("nao_existe")`
- `FireServer("marisco")` sem a Tool equipada
- `FireServer("marisco")` duas vezes seguidas: só a primeira vale (teste com 2 mariscos)
- `FireServer("marisco")` com a fome em 100

### 5. Morte
Com mariscos no inventário, mate o personagem (`Humanoid.Health = 0` no servidor). Depois de renascer, a Tool `Marisco (n)` tem que voltar para a mochila.

### Limpeza
- Apague os scripts temporários.
- **Salve o place.**
